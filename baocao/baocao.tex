\addcontentsline{toc}{section}{LỜI CAM ĐOAN}

Chúng em xin cam đoan rằng đồ án môn học \textit{``Tìm hiểu công nghệ Next.js qua Ứng dụng tra cứu \& khám phá phim ảnh''} là công trình nghiên cứu và phát triển độc lập của nhóm sinh viên thực hiện dưới sự hướng dẫn chuyên môn của ThS. Phạm Thi Vương.

Toàn bộ các số liệu khảo sát, kết quả đo lường thực nghiệm hiệu năng (Core Web Vitals, Bundle Size, Streaming TTFB) và mã nguồn hiện thực được trình bày trong báo cáo này là trung thực, khách quan và xuất phát từ sản phẩm thực tế do nhóm xây dựng. Các đoạn mã tham khảo, thư viện mã nguồn mở và nền tảng giao diện lập trình ứng dụng từ The Movie Database (TMDB) đều được trích dẫn nguồn gốc và tác giả một cách minh bạch, tuân thủ nghiêm ngặt các quy định về trích dẫn học thuật theo chuẩn IEEE.

Nhóm xin chịu hoàn toàn trách nhiệm trước Khoa Công nghệ Thông tin và Trường Đại học Sài Gòn về tính trung thực và liêm chính học thuật của đồ án này.

\section*{LỜI CẢM ƠN}
\addcontentsline{toc}{section}{LỜI CẢM ƠN}

Để hoàn thành đồ án môn học này một cách chỉn chu và đạt được chiều sâu kỹ thuật cao, nhóm chúng em đã nhận được sự quan tâm, tạo điều kiện và hướng dẫn quý báu từ quý Thầy, Cô và các tổ chức liên quan.

Trước hết, nhóm xin gửi lời tri ân chân thành và sâu sắc nhất đến \textbf{ThS. Phạm Thi Vương} -- Giảng viên phụ trách học phần Các Công nghệ Lập trình Hiện đại. Thầy không chỉ truyền đạt những kiến thức nền tảng vững chắc và định hướng tiếp cận công nghệ đúng đắn: \textit{``Trọng tâm của môn học là làm chủ CÔNG NGHỆ, không phải sa đà vào nghiệp vụ phức tạp; ứng dụng xây dựng chỉ là phương tiện để áp dụng và minh họa''}, mà còn luôn nhiệt tình theo sát, giải đáp các vướng mắc kỹ thuật hóc búa và định hướng nhóm giải quyết bài toán cốt lõi.

Nhóm cũng xin chân thành cảm ơn Ban Chủ nhiệm Khoa Công nghệ Thông tin, Trường Đại học Sài Gòn đã xây dựng chương trình đào tạo hiện đại, tạo lập môi trường học tập thực tế giúp sinh viên có cơ hội tiếp cận và làm chủ những công nghệ mới nhất trên thế giới.

Cuối cùng, nhóm xin gửi lời cảm ơn đến cộng đồng mã nguồn mở Next.js (Vercel), React Core Team và nền tảng The Movie Database (TMDB) đã cung cấp các tài liệu kỹ thuật chuẩn xác và nguồn dữ liệu mở chất lượng cao để nhóm hoàn thiện đồ án này.

Dù đã rất nỗ lực nghiên cứu và hoàn thiện, song do thời gian có hạn và kiến thức thực tế còn đang trong quá trình tích lũy, đồ án chắc chắn không tránh khỏi những thiếu sót nhất định. Nhóm rất mong nhận được những lời nhận xét, góp ý quý báu của Thầy Cô để sản phẩm ngày càng hoàn thiện hơn.

\section*{TÓM TẮT ĐỒ ÁN}
\addcontentsline{toc}{section}{TÓM TẮT ĐỒ ÁN}

Trong bối cảnh công nghệ web phát triển vượt bậc, sự chuyển dịch từ kiến trúc Single Page Application (SPA) truyền thống dựa trên Client-Side Rendering (CSR) sang mô hình kiến trúc lai Server-Driven UI kết hợp React Server Components (RSC) đang trở thành xu thế chủ đạo. Báo cáo đồ án này tập trung nghiên cứu chuyên sâu các cơ chế nền tảng và kỹ thuật tiên tiến của nền tảng \textbf{Next.js 16 (App Router)} trên nền tảng \textbf{React 19} và \textbf{TypeScript}, thông qua việc phát triển hệ thống xem và tra cứu phim ảnh trực tuyến mang tên \textbf{MovieHub}.

Dự án khai thác nguồn dữ liệu mở chuẩn RESTful từ The Movie Database (TMDB) API v3 để xây dựng một ứng dụng điện ảnh hoàn chỉnh theo phong cách thiết kế Netflix Dark Cinema. Về mặt kỹ thuật, đồ án giải quyết triệt để các bài toán cốt lõi trong kỹ nghệ phần mềm hiện đại:
\begin{enumerate}[noitemsep]
    \item \textbf{Phân định ranh giới Server/Client Component:} Tối ưu hóa kích thước bundle JavaScript gửi về trình duyệt với cơ chế Zero-Bundle Size của Server Components, bảo vệ khóa API an toàn tuyệt đối trên máy chủ.
    \item \textbf{Data Fetching \& Caching đa tầng:} Triển khai kỹ thuật Incremental Static Regeneration (ISR) với thời gian tái tạo phù hợp theo từng loại dữ liệu, kết hợp song song hóa các truy vấn thông qua \texttt{Promise.all}.
    \item \textbf{Truyền luồng dữ liệu (Streaming UI) với React Suspense:} Loại bỏ hiện tượng chặn hiển thị (blocking request) ở các luồng dữ liệu phụ trợ, cải thiện thời gian phản hồi byte đầu tiên (TTFB) giảm từ $750 \pm 45$ ms xuống còn $180 \pm 15$ ms (giảm 76.0\%), đưa chỉ số vẽ nội dung đầu tiên (FCP) xuống mức $220 \pm 20$ ms.
    \item \textbf{Tương tác dữ liệu bảo mật với Server Actions:} Xử lý tìm kiếm tức thì (Live Search Preview) và quản lý danh sách yêu thích (Watchlist) trực tiếp qua Cookie \texttt{HttpOnly} có kiểm thực dữ liệu đầu vào (Input Validation) nghiêm ngặt, đồng thời cung cấp Route Handler GET chuẩn RESTful đối chứng.
    \item \textbf{Khả năng tự phục hồi (Resilience):} Hiện thực cơ chế DNS Fallback Resolver trên nền Node.js runtime, tự động vượt qua sự cố phân giải tên miền của các nhà mạng viễn thông tại Việt Nam khi kết nối tới TMDB.
    \item \textbf{Tối ưu hóa trải nghiệm người dùng:} Đạt điểm số Google Lighthouse với chỉ số Performance đạt 98/100, các hạng mục Accessibility, Best Practices và SEO đạt 100/100 tuyệt đối; chỉ số ổn định bố cục thị giác CLS đạt mức hoàn hảo 0.000 thông qua component \texttt{next/image}.
\end{enumerate}

Báo cáo được cấu trúc chuẩn mực theo quy trình phát triển phần mềm gồm 4 chương chính: Cơ sở lý thuyết, Phân tích \& Thiết kế hệ thống, Hiện thực hệ thống, Kiểm thử \& Đánh giá hiệu năng, khẳng định năng lực làm chủ công nghệ lập trình web hiện đại của nhóm sinh viên.

\vspace{0.8cm}
\noindent \textbf{Từ khóa:} \textit{Next.js 16, App Router, React Server Components, Server Actions, Streaming Suspense, Incremental Static Regeneration (ISR), TMDB API, DNS Fallback Resolver, Core Web Vitals.}

\textbf{API} & \textit{Application Programming Interface} -- Giao diện lập trình ứng dụng cho phép các hệ thống giao tiếp với nhau. \\
\textbf{CLS} & \textit{Cumulative Layout Shift} -- Chỉ số đo lường mức độ ổn định bố cục thị giác của trang web (tránh hiện tượng gián đoạn, giật màn hình khi tải ảnh). \\
\textbf{CSR} & \textit{Client-Side Rendering} -- Mô hình kết xuất phía máy khách truyền thống trong React SPA, trình duyệt nhận tệp HTML rỗng và tự nạp JavaScript để sinh cây giao diện DOM. \\
\textbf{DNS} & \textit{Domain Name System} -- Hệ thống phân giải tên miền mạng thành địa chỉ IP máy chủ. \\
\textbf{DOM} & \textit{Document Object Model} -- Mô hình đối tượng tài liệu dạng cây biểu diễn cấu trúc trang web của trình duyệt. \\
\textbf{FCP} & \textit{First Contentful Paint} -- Thời điểm trình duyệt bắt đầu vẽ phần tử nội dung DOM đầu tiên lên màn hình. \\
\textbf{ISR} & \textit{Incremental Static Regeneration} -- Cơ chế tái tạo trang tĩnh định kỳ theo thời gian chỉ định (revalidate) mà không cần biên dịch lại toàn bộ dự án. \\
\textbf{LCP} & \textit{Largest Contentful Paint} -- Chỉ số đo thời gian kết xuất phần tử nội dung trực quan lớn nhất trong khung nhìn người dùng. \\
\textbf{PR} & \textit{Pull Request} -- Yêu cầu đóng góp và hợp nhất nhánh tính năng vào nhánh chính có kiểm duyệt mã nguồn chéo. \\
\textbf{REST} & \textit{Representational State Transfer} -- Kiểu kiến trúc tiêu chuẩn cho các dịch vụ web giao tiếp qua giao thức HTTP. \\
\textbf{RPC} & \textit{Remote Procedure Call} -- Giao thức cho phép gọi trực tiếp một hàm thực thi từ xa trên máy chủ qua mạng, nền tảng của Server Actions. \\
\textbf{RSC} & \textit{React Server Components} -- Mô hình component kết xuất trực tiếp trên máy chủ của React 19 và Next.js App Router, loại bỏ hoàn toàn mã JavaScript của component khỏi gói nạp về trình duyệt client. \\
\textbf{SEO} & \textit{Search Engine Optimization} -- Quá trình tối ưu hóa mã nguồn và nội dung để tăng thứ hạng hiển thị trên công cụ tìm kiếm. \\
\textbf{SPA} & \textit{Single Page Application} -- Ứng dụng web đơn trang kết xuất và định tuyến hoàn toàn tại trình duyệt client. \\
\textbf{SSG} & \textit{Static Site Generation} -- Mô hình tạo sẵn toàn bộ tài liệu HTML tĩnh ngay từ thời điểm biên dịch ứng dụng (Build-time rendering). \\
\textbf{SSR} & \textit{Server-Side Rendering} -- Mô hình kết xuất HTML động từ máy chủ cho mỗi lượt truy cập (Request-time rendering). \\
\textbf{TMDB} & \textit{The Movie Database} -- Nguồn cung cấp RESTful API công cộng dữ liệu phim điện ảnh và truyền hình trực tuyến. \\
\textbf{TTFB} & \textit{Time to First Byte} -- Thời gian phản hồi từ lúc client gửi request đến khi nhận được byte dữ liệu đầu tiên từ server. \\
\bottomrule
\end{longtable}

\section*{LỜI MỞ ĐẦU}
\addcontentsline{toc}{section}{LỜI MỞ ĐẦU}

\paragraph*{1. Tính cấp thiết của đề tài}
Trong hơn một thập kỷ qua, hệ sinh thái phát triển ứng dụng web đã chứng kiến sự thống trị áp đảo của thư viện React cùng mô hình kiến trúc Single Page Application (SPA). Mặc dù mô hình này mang lại trải nghiệm chuyển trang mượt mà, nhưng theo thời gian và sự gia tăng phức tạp của các ứng dụng thương mại, kiến trúc Client-Side Rendering (CSR) đã bộc lộ những nhược điểm cố hữu nghiêm trọng:
\begin{itemize}[noitemsep]
    \item \textbf{Tải trọng gói mã nguồn (Bundle Size) quá lớn:} Trình duyệt client phải tải về hàng megabyte mã JavaScript, sau đó tiến hành phân tích cú pháp (parse) và thực thi (execute) trước khi người dùng có thể nhìn thấy nội dung trang web.
    \item \textbf{Ảnh hưởng tiêu cực đến chỉ số trải nghiệm người dùng:} Thời gian hiển thị nội dung đầu tiên (FCP) và thời gian hiển thị nội dung chính (LCP) bị kéo dài, gây thất thoát người dùng ngay từ những giây đầu truy cập.
    \item \textbf{Hạn chế nghiêm trọng về SEO:} Các bot tìm kiếm của Google, Bing hoặc các trình thu thập siêu dữ liệu mạng xã hội (Facebook, Twitter) thường không thực thi hoàn chỉnh mã JavaScript phức tạp, chỉ ghi nhận tài liệu HTML rỗng với thẻ \texttt{<div id="root"></div>}.
    \item \textbf{Nguy cơ lộ lọt bí mật bảo mật:} Việc gọi trực tiếp các API của bên thứ ba từ phía trình duyệt đòi hỏi phải nhúng các khóa API (API Key, Secret Token) vào mã nguồn JavaScript gửi xuống máy khách, dễ dàng bị khai thác và đánh cắp.
\end{itemize}

Sự ra đời của nền tảng Next.js [1] với kiến trúc App Router dựa trên nền tảng React 19 [2] và React Server Components (RSC) [7] đã đánh dấu một bước chuyển dịch mang tính cách mạng: chuyển dịch trọng tâm kết xuất về phía máy chủ (Server-Driven UI). Bằng cách kết xuất mã nguồn trên máy chủ và chỉ gửi về client luồng HTML nhẹ kèm luồng cấu trúc dữ liệu RSC Payload, Next.js loại bỏ hoàn toàn mã JavaScript của Server Component khỏi gói nạp máy khách, đem lại lợi ích Zero-Bundle Size vượt trội, bảo vệ bí mật máy chủ tuyệt đối và mở ra khả năng tối ưu hóa công cụ tìm kiếm chuẩn mực.

Quán triệt tư tưởng chỉ đạo của học phần Các Công nghệ Lập trình Hiện đại: \textit{``Trọng tâm của môn học là làm chủ CÔNG NGHỆ, không phải sa đà vào nghiệp vụ phức tạp; ứng dụng xây dựng chỉ là phương tiện để áp dụng và minh họa''}, nhóm sinh viên chúng em thực hiện đề tài: \textbf{``Tìm hiểu công nghệ Next.js qua Ứng dụng tra cứu \& khám phá phim ảnh''}. Bằng việc lựa chọn nguồn dữ liệu có sẵn từ The Movie Database (TMDB) API v3 [3], toàn bộ nguồn lực và công sức của nhóm được tập trung tuyệt đối vào việc làm chủ các cơ chế kỹ thuật cốt lõi của Next.js.

\paragraph*{2. Mục tiêu nghiên cứu của đồ án}
Đồ án bám sát khung chuẩn đánh giá 3 tầng của môn học:
\begin{enumerate}[noitemsep]
    \item \textbf{Tầng 1A (Mục tiêu bắt buộc lõi):}
    \begin{itemize}[noitemsep]
        \item Nắm vững cấu trúc thư mục App Router định tuyến theo tệp tin (\texttt{app/layout.tsx}, \texttt{app/page.tsx}).
        \item Phân định rõ ràng ranh giới giữa Server Components (chạy mặc định trên máy chủ) và Client Components (khai báo chỉ thị \texttt{"use client"}).
        \item Thực hiện thu thập dữ liệu (Data Fetching) hoàn toàn phía máy chủ, bảo mật tuyệt đối các thông số môi trường và khóa API.
    \end{itemize}
    \item \textbf{Tầng 1B (Mục tiêu nâng cao theo đặc thù ứng dụng):}
    \begin{itemize}[noitemsep]
        \item Làm chủ định tuyến động (Dynamic Routing) \texttt{/movie/[id]} xử lý tham số bất đồng bộ dạng Promise (bắt đầu từ Next.js 15 và trở thành quy chuẩn bắt buộc trong Next.js 16).
        \item Triển khai cơ chế Streaming UI kết hợp React Suspense và khung sườn chờ (Skeleton Loading) để giảm thời gian phản hồi byte đầu tiên (TTFB).
        \item Ứng dụng cơ chế Caching dữ liệu tĩnh có kiểm soát thời hạn Incremental Static Regeneration (ISR) trong tầng dịch vụ.
        \item Xây dựng các chức năng tương tác dữ liệu bảo mật thông qua Server Actions (\texttt{"use server"}) đọc/ghi Cookie an toàn.
        \item Tối ưu hóa đa phương tiện và xử lý hình ảnh chống hiện tượng giật màn hình (Zero CLS) bằng component \texttt{next/image}.
        \item Tự động hóa SEO thông qua hàm \texttt{generateMetadata} trích xuất thông tin động.
    \end{itemize}
    \item \textbf{Tầng 2 (Mục tiêu chuẩn kỹ nghệ phần mềm):}
    \begin{itemize}[noitemsep]
        \item Quản lý mã nguồn theo mô hình Git Flow phân nhánh chuyên nghiệp, kiểm duyệt mã thông qua Pull Request.
        \item Đảm bảo tính nhất quán và an toàn mã nguồn với TypeScript chế độ nghiêm ngặt (Strict Mode).
        \item Hiện thực giải pháp xử lý ngoại lệ mạng chuyên sâu: Tự động phân giải địa chỉ DNS (DNS Fallback Resolver) khi kết nối tới máy chủ dữ liệu quốc tế bị gián đoạn.
        \item Tuân thủ nghiêm ngặt hệ thống thiết kế chuẩn điện ảnh Netflix Dark Cinema (\texttt{DESIGN.md}).
    \end{itemize}
\end{enumerate}

\section{CƠ SỞ LÝ THUYẾT VÀ CÔNG NGHỆ SỬ DỤNG}

\subsection{Tổng quan về Next.js và lịch sử phát triển}

\subsubsection{Bối cảnh ra đời và hạn chế của React Single Page Application (SPA)}
Kể từ khi được Facebook giới thiệu vào năm 2013, thư viện React đã tạo nên cuộc cách mạng trong thiết kế giao diện nhờ mô hình Virtual DOM và tư duy phát triển dựa trên Component. Tuy nhiên, mô hình ứng dụng đơn trang (SPA) dựa trên cơ chế Client-Side Rendering (CSR) đã bộc lộ những nhược điểm lớn khi mở rộng quy mô:
\begin{enumerate}[noitemsep]
    \item \textbf{Hiện tượng trang trắng ban đầu (Blank Page):} Trình duyệt nhận về tệp tin HTML gần như rỗng chỉ chứa một phần tử \texttt{<div id="root"></div>}. Người dùng phải đợi trình duyệt tải xong toàn bộ gói mã nguồn JavaScript, sau đó chạy mã để dựng cây DOM thực tế.
    \item \textbf{Tải trọng mạng và chi phí xử lý của thiết bị di động:} Các gói thư viện phụ thuộc (npm packages) đều bị đóng gói dồn vào bundle của client. Trên các thiết bị di động cấu hình yếu, việc phân tích cú pháp (parse) và biên dịch (compile) tệp JavaScript nặng hàng megabyte gây đơ giật giao diện và kéo dài chỉ số Time to Interactive (TTI).
    \item \textbf{Thách thức về SEO và Social Sharing:} Các hệ thống lập chỉ mục tìm kiếm và robot thu thập dữ liệu mạng xã hội (Open Graph) thường không thực thi hoàn chỉnh các luồng JavaScript bất đồng bộ, khiến website bị xếp hạng thấp hoặc không hiển thị được ảnh đại diện xem trước.
\end{enumerate}

\subsubsection{Bước chuyển đổi với Pages Router (Next.js 1 -- 12)}
Nhằm khắc phục các điểm yếu của React SPA, Vercel đã giới thiệu nền tảng Next.js vào năm 2016 [1]. Kiến trúc Pages Router tổ chức các trang web tương ứng với các tệp tin trong thư mục \texttt{pages/}, đồng thời cung cấp hai cơ chế tiền kết xuất mạnh mẽ:
\begin{itemize}[noitemsep]
    \item \textbf{Server-Side Rendering (SSR) với \texttt{getServerSideProps}:} Máy chủ thực thi lấy dữ liệu và kết xuất mã HTML hoàn chỉnh cho từng request của người dùng trước khi gửi về client.
    \item \textbf{Static Site Generation (SSG) với \texttt{getStaticProps}:} Máy chủ tạo sẵn tài liệu HTML ngay tại thời điểm biên dịch ứng dụng (Build-time), mang lại tốc độ phản hồi cực nhanh thông qua mạng phân phối nội dung (CDN).
\end{itemize}

Tuy nhiên, Pages Router vẫn tồn tại hạn chế về mặt kiến trúc gọi là \textbf{Chi phí Hydration toàn bộ (Hydration Overhead)}. Sau khi máy chủ gửi tài liệu HTML về client, trình duyệt vẫn bắt buộc phải tải về toàn bộ mã nguồn JavaScript của toàn bộ trang để tiến hành quá trình ``Hydrate'' -- gắn các trình lắng nghe sự kiện (Event Listeners) vào các nút DOM tĩnh. Điều này đồng nghĩa với việc mã nguồn của các component chỉ hiển thị nội dung tĩnh (như Header, Footer, Sidebar) vẫn bị gửi xuống client một cách dư thừa.

\subsubsection{Kỷ nguyên mới với App Router và Server-Driven UI (Next.js 13 -- 16)}
Nhận thức được giới hạn của kiến trúc cũ, đội ngũ kỹ sư Vercel phối hợp chặt chẽ cùng React Core Team đã phát triển kiến trúc \textbf{App Router}, được chính thức đưa vào sản xuất từ Next.js 13 và hoàn thiện vững chắc trong Next.js 16 [1].

App Router được xây dựng xung quanh khái niệm \textbf{React Server Components (RSC)} [7]. Trọng tâm kết xuất được chuyển dịch triệt để về phía máy chủ (Server-Driven UI). Trong mô hình này, các component mặc định chỉ chạy trên máy chủ, cho phép truy cập trực tiếp vào hệ thống tệp, cơ sở dữ liệu và biến môi trường bảo mật mà không gửi một dòng mã lệnh JavaScript nào của component đó xuống trình duyệt.

\subsubsection{Phản biện kỹ thuật: Khi nào KHÔNG nên sử dụng Next.js?}
Dựa trên trải nghiệm thực tế trong quá trình phát triển dự án MovieHub, nhóm nhận thấy Next.js không phải là giải pháp vạn năng cho mọi bài toán công nghệ. Dưới đây là các kịch bản thực tế mà việc sử dụng Next.js mang lại nhiều bất lợi hơn là ưu điểm:
\begin{enumerate}[noitemsep]
    \item \textbf{Ứng dụng nội bộ hoặc Bảng điều khiển quản trị (Internal Dashboard / CMS sau đăng nhập):} Các hệ thống này hoàn toàn không có nhu cầu tối ưu hóa công cụ tìm kiếm (SEO) hay chia sẻ liên kết mạng xã hội. Việc sử dụng Next.js làm gia tăng độ phức tạp hạ tầng máy chủ và rủi ro Hydration Mismatch một cách không cần thiết; một giải pháp Single Page Application thuần với React + Vite sẽ nhẹ nhàng, dễ bảo trì và tiết kiệm chi phí vận hành hơn rất nhiều.
    \item \textbf{Website nội dung tĩnh đơn giản (Blog cá nhân, Landing Page, Tài liệu hướng dẫn):} Việc cấu hình một máy chủ Node.js với App Router để phục vụ các nội dung hầu như không biến động là lãng phí tài nguyên. Astro với kiến trúc Islands hoặc static site generator đơn giản sẽ mang lại hiệu năng cao hơn với 0 KB JavaScript gửi về mặc định.
    \item \textbf{Đội ngũ phát triển chưa quen với ranh giới Server/Client và chi phí hạ tầng:} Sự phân chia nghiêm ngặt giữa môi trường Node.js và trình duyệt (Server Components không có window/DOM/useEffect, async params, Server Actions POST queue) tạo ra một rào cản học tập (Learning Curve) dốc đứng. Ngoài ra, việc tự triển khai Next.js (Self-hosting ngoài Vercel) đòi hỏi cấu hình phức tạp về Cache Handler, ISR phân tán và duy trì tiến trình Node.js liên tục, dẫn đến chi phí vận hành cao hơn so với lưu trữ tĩnh trên CDN.
\end{enumerate}

\subsection{Kiến trúc React Server Components (RSC) và Client Components}

\subsubsection{Bản chất và nguyên lý hoạt động của RSC}
Khác với component React truyền thống (chạy trên cả server và client trong quá trình SSR), \textbf{React Server Component (RSC)} là một loại component đặc biệt chỉ thực thi duy nhất trên môi trường máy chủ [7]. 

Khi một yêu cầu được gửi tới máy chủ Next.js:
\begin{enumerate}[noitemsep]
    \item Máy chủ thực thi hàm component (hỗ trợ hàm bất đồng bộ \texttt{async/await} trực tiếp ở cấp cao nhất).
    \item Máy chủ gọi dữ liệu từ cơ sở dữ liệu hoặc dịch vụ bên ngoài (TMDB API) mà không cần dùng hook \texttt{useEffect}.
    \item Thay vì sinh ra mã JavaScript để gửi về trình duyệt, máy chủ tuần tự hóa (serialize) cây component thành một luồng dữ liệu nhị phân/văn bản có cấu trúc gọi là \textbf{RSC Payload}.
    \item RSC Payload chứa cấu trúc của cây giao diện, các thuộc tính props được truyền và vị trí đánh dấu (placeholders) nơi các Client Component cần được nạp và hydrate.
\end{enumerate}

Nhờ cơ chế này, toàn bộ các thư viện hỗ trợ nặng (như thư viện xử lý chuỗi, định dạng ngày tháng, tính toán phức tạp) đều chỉ tồn tại trên máy chủ và hoàn toàn không làm tăng kích thước bundle của trình duyệt client (nguyên lý \textbf{Zero-Bundle Size}).

\subsubsection{Chỉ thị \texttt{"use client"} và quy tắc Composition Pattern}
Trong Next.js App Router, mọi tệp tin component mặc định là Server Component. Để chuyển đổi một component sang Client Component, lập trình viên phải đặt chỉ thị \texttt{"use client"} ở dòng đầu tiên của tệp tin. Chỉ thị này xác định một \textbf{Ranh giới mạng (Network Boundary)}, báo hiệu cho trình biên dịch rằng toàn bộ component này cùng các module được nó import sẽ được đóng gói gửi về client để thực hiện hydration.

Các trường hợp bắt buộc phải sử dụng Client Component bao gồm:
\begin{itemize}[noitemsep]
    \item Cần lắng nghe sự kiện tương tác của người dùng: \texttt{onClick}, \texttt{onChange}, \texttt{onSubmit}.
    \item Cần quản lý trạng thái động hoặc vòng đời: \texttt{useState}, \texttt{useReducer}, \texttt{useEffect}.
    \item Cần truy cập các API riêng của trình duyệt: \texttt{localStorage}, \texttt{sessionStorage}, \texttt{window}, \texttt{document}.
    \item Cần sử dụng các React Custom Hooks quản lý giao diện tương tác.
\end{itemize}

Để duy trì hiệu năng tối ưu, đồ án tuân thủ nghiêm ngặt mô hình \textbf{Composition Pattern}: Đẩy các Client Component xuống các nút lá nhỏ nhất của cây giao diện (ví dụ: nút bấm mở modal \texttt{TrailerModal}, thanh cuộn \texttt{MovieRow}), giữ cho các component cha (như \texttt{app/page.tsx}, \texttt{app/layout.tsx}) là Server Components để thực hiện lấy dữ liệu tập trung.

\subsection{Cơ chế Caching và Data Fetching đa tầng trong Next.js 16}

Dự án MovieHub được xây dựng trên nền tảng \textbf{Next.js 16.3.6} và \textbf{React 19.2.8}. Một trong những thay đổi quan trọng nhất của Next.js kể từ phiên bản 15 và 16 là sự chuyển dịch mô hình bộ nhớ đệm: Hàm \texttt{fetch} mặc định không còn tự động lưu đệm vĩnh viễn (\texttt{force-cache}) như thời Next.js 14, mà chuyển sang mặc định \texttt{no-store} trừ khi lập trình viên chủ động khai báo chiến lược lưu trữ.

\subsubsection{Tính hợp lệ của API \texttt{fetch(url, \{ next: \{ revalidate \} \})}}
Một số quan điểm cho rằng cú pháp \texttt{fetch(url, \{ next: \{ revalidate: seconds \} \})} là cơ chế cũ của Next.js 13/14 và bị thay thế hoàn toàn trong Next.js 16. Tuy nhiên, theo tài liệu đặc tả chính thức của Vercel (\url{https://nextjs.org/docs/app/api-reference/functions/fetch}), đây vẫn là \textbf{API chuẩn mực, ổn định (Stable API) và hoàn toàn hợp lệ} trong Next.js 16 để điều khiển \textbf{Data Cache ở cấp độ yêu cầu mạng (Request-level Caching)}:
\begin{equation}
\text{fetch}(\text{url}, \{\, \text{next}: \{\, \text{revalidate}: 3600 \,\} \,\})
\end{equation}

Nguyên lý hoạt động theo cơ chế \textbf{Stale-While-Revalidate}:
\begin{itemize}[noitemsep]
    \item Trong khoảng thời gian TTL (ví dụ 3600 giây), mọi yêu cầu truy vấn đến endpoint tương ứng đều được phục vụ trực tiếp từ Next.js Data Cache trên máy chủ với độ trễ dưới 10ms.
    \item Sau khi hết hạn TTL, khi có lượt truy cập mới, máy chủ phục vụ bản dữ liệu cũ trước (stale), đồng thời kích hoạt một tiến trình nền bất đồng bộ (Background Revalidation) để gọi API TMDB lấy dữ liệu mới và cập nhật bản ghi cache.
    \item Lượt truy cập tiếp theo sẽ nhận được dữ liệu hoàn toàn mới mà không gây nghẽn luồng xử lý chính.
\end{itemize}

\subsubsection{Cơ chế Cache Components (\texttt{"use cache"} và \texttt{cacheLife}) trong Next.js 16}
Bên cạnh Request Data Cache truyền thống, Next.js 16 giới thiệu kiến trúc bộ nhớ đệm cấp độ component mang tên \textbf{Cache Components} (trước đây là cờ thử nghiệm \texttt{dynamicIO}):
\begin{itemize}[noitemsep]
    \item \textbf{Trạng thái trong dự án:} Tính năng này hiện vẫn là cờ tùy chọn (Opt-in Experimental) và \textbf{mặc định bị tắt (\texttt{cacheComponents: false})} trong cấu hình gốc \texttt{next.config.ts} của Next.js 16. Dự án MovieHub chủ động giữ \texttt{cacheComponents: false} để đảm bảo tính ổn định cao nhất cho môi trường sản xuất (Production-ready).
    \item \textbf{Cơ chế hoạt động khi được kích hoạt:} Nếu bật \texttt{cacheComponents: true}, lập trình viên sử dụng chỉ thị \texttt{"use cache"} ở đầu async function hoặc component, kết hợp hàm cấu hình vòng đời \texttt{cacheLife()}:
    \begin{itemize}[noitemsep]
        \item \texttt{cacheLife("seconds")}: \texttt{revalidate: 1s, expire: 60s}.
        \item \texttt{cacheLife("minutes")}: \texttt{revalidate: 60s, expire: 1h}.
        \item \texttt{cacheLife("hours")}: \texttt{revalidate: 1h, expire: 24h}.
        \item \texttt{cacheLife("days")}: \texttt{revalidate: 24h, expire: 7d}.
        \item \texttt{cacheLife("default")}: \texttt{revalidate: 15m, expire: $\infty$}.
    \end{itemize}
    Ưu điểm của Cache Components là có thể lưu đệm cả kết quả tính toán phức tạp hoặc truy vấn cơ sở dữ liệu trực tiếp, không phụ thuộc vào lệnh \texttt{fetch}.
\end{itemize}

\subsubsection{Tác động của việc đọc \texttt{cookies()} đến quá trình Render và Caching}
Trong kiến trúc Next.js App Router, việc truy cập các Dynamic Functions (như \texttt{cookies()}, \texttt{headers()}) sẽ tự động chuyển tuyến đường đó sang chế độ \textbf{Dynamic Rendering (kết xuất động theo từng yêu cầu)}:
\begin{itemize}[noitemsep]
    \item \textbf{Các tuyến đường thực tế đọc cookie trong MovieHub:} 
    \begin{enumerate}[noitemsep]
        \item Tuyến \texttt{/watchlist} (\texttt{app/watchlist/page.tsx}): Gọi \texttt{await getWatchlistIds()} đọc cookie \texttt{mh\_watchlist} để lấy danh sách phim cá nhân hóa của người dùng.
        \item Tuyến \texttt{/movie/[id]} (\texttt{app/movie/[id]/page.tsx}): Gọi \texttt{await isMovieSaved(id)} để xác định trạng thái ban đầu của nút lưu phim (\texttt{WatchlistButton}).
        \item Tệp Server Action \texttt{app/actions/watchlist.ts}: Thao tác trực tiếp với \texttt{cookies()} để thêm/xóa phim.
    \end{enumerate}
    \item \textbf{Đính chính về Header và MovieCard:} Cần lưu ý rằng component \texttt{Header} (\texttt{components/client/Header.tsx}) và \texttt{MovieCard} (\texttt{components/server/MovieCard.tsx}) \textbf{hoàn toàn không đọc cookie}. \texttt{Header} chỉ lắng nghe sự kiện cuộn trang (\texttt{scrollY}) và đường dẫn URL (\texttt{usePathname}); \texttt{MovieCard} là một Server Component thuần nhận dữ liệu phim qua props tĩnh.
\end{itemize}

\subsubsection{Mối quan hệ tương hỗ giữa Streaming Suspense và Data Caching}
Kỹ thuật truyền luồng (Streaming với React Suspense) và Caching dữ liệu (ISR) \textbf{không hề loại trừ nhau}, mà hỗ trợ lẫn nhau theo hai giai đoạn rõ rệt:
\begin{enumerate}[noitemsep]
    \item \textbf{Khi phục vụ bản ghi đã có trong Cache (Cache Hit):} Toàn bộ tài liệu HTML và RSC Payload đã được chuẩn bị sẵn; máy chủ gửi về trình duyệt tức thì mà không phải chờ đợi bất kỳ lời gọi API nào.
    \item \textbf{Khi tạo mới trang động hoặc tái tạo nền (Cache Miss / Dynamic Stream):} Tại tuyến đường \texttt{/movie/[id]}, máy chủ gửi ngay phần khung chính của bộ phim (Poster, Tiêu đề, Tóm tắt) qua kỹ thuật HTTP Chunked Transfer Encoding. Trong khi người dùng đã nhìn thấy giao diện chính, các khối phụ như danh sách diễn viên (\texttt{CastList}) và phim đề xuất (\texttt{SimilarMovies}) được server stream về sau. Đồng thời, bên dưới Server, các lệnh \texttt{fetchTMDB} gọi TMDB API vẫn tự động lưu kết quả vào Data Cache với thời hạn 3600s, giúp các yêu cầu tiếp theo đạt tốc độ tối đa.
\end{enumerate}

\subsubsection{Các cơ chế nền tảng bổ trợ: Hydration, Vòng đời Hook và URL State}
Để đảm bảo trải nghiệm người dùng hoàn chỉnh, dự án tích hợp chặt chẽ các cơ chế nền tảng bắt buộc của lập trình web hiện đại:
\begin{itemize}[noitemsep]
    \item \textbf{Cơ chế Client Hydration và phòng chống Hydration Mismatch:} Sau khi trình duyệt nhận được HTML render sẵn từ server, React gắn kết các bộ lắng nghe sự kiện (event listeners) vào DOM. Để tránh lỗi bất đồng bộ giữa cây DOM server và client (Hydration Mismatch), các trạng thái phụ thuộc vào trình duyệt (như trạng thái cuộn chuột \texttt{window.scrollY} trong \texttt{Header}) chỉ được kích hoạt bên trong hook \texttt{useEffect} sau khi component đã mount thành công trên client.
    \item \textbf{Quản lý trạng thái thông qua URL (\texttt{searchParams}):} Tại các trang \texttt{/browse} và \texttt{/search}, toàn bộ trạng thái bộ lọc (thể loại, năm, sắp xếp, trang hiện tại) được lưu trữ trực tiếp trên URL Query Parameters. Cách tiếp cận này giúp người dùng có thể chia sẻ liên kết kết quả lọc, lưu bookmark trình duyệt, và sử dụng các nút Back/Forward mà không bị mất trạng thái. Thư viện hook \texttt{useTransition} kết hợp \texttt{useRouter.replace()} giúp cập nhật URL mượt mà mà không gây đơ cứng giao diện.
    \item \textbf{Tối ưu hóa điều hướng với \texttt{next/link}:} Mọi liên kết chuyển trang đều sử dụng thẻ \texttt{<Link>} của Next.js. Component này tự động kích hoạt cơ chế Viewport Prefetching: Khi một thẻ liên kết cuộn vào tầm nhìn của màn hình, Next.js sẽ nạp trước RSC Payload của tuyến đường đích trong nền, giúp việc chuyển trang diễn ra tức thì như một ứng dụng đơn trang (SPA).
\end{itemize}

\subsection{Kỹ thuật Streaming UI và React Suspense}

\subsubsection{Hạn chế của SSR truyền thống (All-or-Nothing Problem)}
Trong mô hình Server-Side Rendering truyền thống, quá trình kết xuất trang web mắc phải bài toán thắt nút cổ chai ``Tất cả hoặc Không có gì'' (All-or-Nothing):
\begin{enumerate}[noitemsep]
    \item Máy chủ bắt buộc phải đợi \textbf{tất cả} các truy vấn dữ liệu từ cơ sở dữ liệu và API bên ngoài hoàn thành thì mới có thể bắt đầu tạo tài liệu HTML. Nếu có một API phản hồi chậm (ví dụ: API lấy danh sách diễn viên hoặc phim tương tự mất 800ms), toàn bộ trang web sẽ bị chặn và trình duyệt không hiển thị bất cứ thứ gì.
    \item Trình duyệt client phải tải về toàn bộ mã JavaScript của cả trang thì mới có thể tiến hành hydrate.
\end{enumerate}

\subsubsection{Cơ chế Streaming HTML lũy tiến}
Next.js App Router kết hợp cùng tính năng \textbf{React Suspense} của React 19 giải quyết triệt để vấn đề trên thông qua cơ chế truyền luồng (Streaming) [2]. Máy chủ phân rã trang web thành nhiều khối (chunks) độc lập:
\begin{itemize}[noitemsep]
    \item Phần khung chính của trang (Header, thông tin tóm tắt phim) vốn có dữ liệu nhanh sẽ được máy chủ kết xuất và gửi về trình duyệt ngay lập tức cùng với khung giao diện chờ (Skeleton Loader) của phần dữ liệu chậm.
    \item Người dùng có thể nhìn thấy nội dung chính và đọc thông tin phim ngay tại thời điểm 180ms đầu tiên.
    \item Các Server Component xử lý dữ liệu nặng (như \texttt{CastSlider} và \texttt{SimilarMoviesSlider}) được bọc bên trong thẻ \texttt{<Suspense fallback=\{<Skeleton />\}>}. Khi các truy vấn này hoàn tất trên server, máy chủ sẽ gửi tiếp một đoạn stream HTML chứa nội dung thực tế qua cùng một kết nối HTTP đang mở để tự động thay thế phần Skeleton mà không cần tải lại trang.
\end{itemize}

\subsection{Cơ chế Server Actions và xử lý Mutation dữ liệu}

\subsubsection{Kiến trúc Remote Procedure Call (RPC)}
Trước khi có Server Actions, để thực hiện một tác vụ tương tác dữ liệu từ máy khách (như thêm phim vào danh sách yêu thích, tìm kiếm gợi ý), lập trình viên bắt buộc phải thực hiện quy trình thủ công:
\begin{enumerate}[noitemsep]
    \item Tạo một endpoint API Route riêng biệt (ví dụ: \texttt{/api/watchlist}).
    \item Viết mã kiểm tra phương thức HTTP (POST/DELETE), đọc tham số từ body.
    \item Phía client sử dụng lệnh \texttt{fetch('/api/watchlist')} với các bước cấu hình headers phức tạp.
\end{enumerate}

Với \textbf{Server Actions}, Next.js giới thiệu mô hình gọi thủ tục từ xa (RPC) tích hợp sâu vào cây component. Lập trình viên chỉ cần khai báo một hàm bất đồng bộ với chỉ thị \texttt{"use server"}:
\begin{lstlisting}[language=TypeScript]
// app/actions/watchlist.ts
"use server";

import { cookies } from "next/headers";
import { revalidatePath } from "next/cache";

export async function addToWatchlistAction(movie: MovieItem) {
  const cookieStore = await cookies();
  // Xu ly doc ghi truc tiep tren HTTP Cookie an toan
  revalidatePath("/watchlist");
  return { success: true };
}
\end{lstlisting}

Trình biên dịch của Next.js sẽ tự động mã hóa hàm này thành một định danh duy nhất và thiết lập một lời gọi POST HTTP bảo mật ngầm định.

\subsubsection{Bảo mật dữ liệu, kiểm thực đầu vào và giới hạn Cookie HttpOnly}
Server Actions thực thi hoàn toàn trong môi trường máy chủ bảo mật, mang lại các lợi thế kỹ thuật vượt trội nhưng cũng đòi hỏi các biện pháp bảo vệ đi kèm:
\begin{itemize}[noitemsep]
    \item \textbf{Cơ chế bảo vệ của Cookie HttpOnly:} Việc cấu hình cờ \texttt{httpOnly: true} và \texttt{secure: true} ngăn chặn mã độc JavaScript phía client truy cập hoặc đọc trực tiếp giá trị cookie thông qua \texttt{document.cookie}. Điều này giúp triệt tiêu nguy cơ kẻ tấn công đánh cắp cookie lưu trữ phiên làm việc hoặc danh sách cá nhân hóa thông qua các kịch bản Cross-Site Scripting (XSS), mặc dù bản thân lỗ hổng XSS trên giao diện vẫn cần được phòng chống bằng việc lọc và khử mã độc dữ liệu hiển thị.
    \item \textbf{Kiểm thực dữ liệu đầu vào (Input Validation) trên Server Actions:} Do Server Actions bản chất là các endpoint HTTP POST công khai được Next.js sinh ra ngầm định, bất kỳ client nào cũng có thể gửi request trực tiếp tới. Do đó, đồ án thực hiện kiểm thực dữ liệu đầu vào nghiêm ngặt phía server (kiểm tra kiểu số nguyên dương hợp lệ cho \texttt{movieId}, giới hạn độ dài chuỗi tìm kiếm từ 2 đến 100 ký tự và loại bỏ các ký tự điều khiển nguy hiểm).
    \item \textbf{Giới hạn kích thước Cookie theo chuẩn RFC 6265:} Giao thức HTTP quy định kích thước tối đa của mỗi cookie không vượt quá 4096 bytes (4KB). Khi lưu trữ mảng các mã định danh phim yêu thích (\texttt{mh\_watchlist}) dưới dạng chuỗi JSON mã hóa \texttt{[550, 680, 299536, ...]}, đồ án thiết lập ngưỡng giới hạn tối đa 200 phim (chiếm khoảng 1.5 KB), bảo đảm danh sách không bao giờ bị cắt xén hay bị trình duyệt từ chối do vượt quá trần 4KB.
    \item \textbf{Tự động đồng bộ giao diện qua \texttt{revalidatePath}:} Tích hợp tính năng làm mới bộ nhớ đệm (\texttt{revalidatePath('/watchlist')}), đảm bảo ngay sau khi action kết thúc, giao diện người dùng tự động phản ánh trạng thái dữ liệu mới nhất mà không cần quản lý state thủ công.
\end{itemize}

\subsection{Nền tảng dữ liệu mở The Movie Database (TMDB) API}

The Movie Database (TMDB) [3] là cơ sở dữ liệu mở phổ biến nhất trên thế giới về phim điện ảnh và chương trình truyền hình. Hệ sinh thái MovieHub khai thác các nhóm dịch vụ REST API v3 của TMDB:
\begin{itemize}[noitemsep]
    \item \textbf{Nhóm dữ liệu thịnh hành và danh mục:} \texttt{/trending/}\allowbreak\texttt{movie/week}, \texttt{/movie/}\allowbreak\texttt{popular}, \texttt{/movie/}\allowbreak\texttt{top\_rated}, \texttt{/movie/}\allowbreak\texttt{upcoming}.
    \item \textbf{Nhóm dữ liệu chi tiết đa chiều:} \texttt{/movie/\{id\}} (thông tin tóm tắt), \texttt{/movie/\{id\}/credits} (dàn diễn viên và đạo diễn), \texttt{/movie/\{id\}/videos} (danh sách video trailer YouTube), \texttt{/movie/\{id\}/similar} (danh sách phim tương đồng).
    \item \textbf{Nhóm dữ liệu khám phá và lọc động:} \texttt{/discover/movie} hỗ trợ lọc theo thể loại (\texttt{with\_genres}), sắp xếp (\texttt{sort\_by}), điểm số tối thiểu (\texttt{vote\_average.gte}) và năm phát hành (\texttt{primary\_release\_year}).
    \item \textbf{Nhóm dữ liệu phim truyền hình và tìm kiếm:} \texttt{/tv/popular} và \texttt{/search/multi}.
\end{itemize}

\subsection{Thiết kế tích hợp dịch vụ và luồng dữ liệu}

\subsubsection{Kiến trúc tầng dịch vụ \texttt{services/tmdb.ts}}
Tất cả các lời gọi mạng ra ngoài TMDB đều được tập trung vào hàm cốt lõi \texttt{fetchTMDB<T>()}. Hàm này chịu trách nhiệm:
\begin{enumerate}[noitemsep]
    \item Tự động gắn tiền tố địa chỉ máy chủ \texttt{https://api.themoviedb.org/3}.
    \item Tự động đính kèm mã xác thực bí mật thông qua HTTP Header \texttt{Authorization: Bearer <TOKEN>}.
    \item Kiểm soát lỗi mạng và mã trạng thái HTTP, trả về thông báo lỗi chuẩn xác hoặc kích hoạt cơ chế dự phòng khi có sự cố.
\end{enumerate}

\subsubsection{Giải pháp kiến trúc DNS Fallback Resolver}
Trong quá trình triển khai thực tế trên mạng Internet tại Việt Nam, nhóm nghiên cứu phát hiện một thách thức lớn từ hạ tầng mạng: Một số nhà cung cấp dịch vụ mạng (ISP) thỉnh thoảng chặn hoặc trả về mã lỗi \texttt{ENOTFOUND} đối với tên miền \texttt{api.themoviedb.org} do xung đột chính sách DNS.

Về mặt kỹ thuật, hàm \texttt{dns.setServers()} của Node.js chỉ có hiệu lực với nhóm hàm \texttt{dns.resolve*}, hoàn toàn không tác động đến hàm \texttt{dns.lookup} mà API \texttt{fetch} mặc định sử dụng để mở kết nối TCP/IP. Do đó, để đảm bảo tính sẵn sàng cao (NFR04), nhóm đã thiết kế giải pháp can thiệp trực tiếp vào cơ chế phân giải tên miền:
\begin{itemize}[noitemsep]
    \item Khởi tạo một đối tượng phân giải độc lập \texttt{dns.promises.Resolver()} với danh sách máy chủ DNS công cộng quốc tế uy tín: Google DNS (\texttt{8.8.8.8}) và Cloudflare DNS (\texttt{1.1.1.1}).
    \item Ghi đè (hook/override) hàm \texttt{dns.lookup} của Node.js: Khi phát hiện yêu cầu phân giải tên miền chứa \texttt{themoviedb.org}, hệ thống sẽ sử dụng \texttt{resolver.resolve4()} để lấy trực tiếp địa chỉ IPv4 từ Google/Cloudflare, bỏ qua DNS mặc định của nhà mạng.
    \item \textbf{Phạm vi áp dụng và giới hạn:} Cơ chế này chỉ thực thi trên môi trường Node.js Server Runtime (không áp dụng trên Edge Runtime). Khi triển khai trên các nền tảng đám mây quốc tế (như Vercel), hạ tầng DNS toàn cầu đã ổn định nên cơ chế này đóng vai trò là lớp bảo vệ dự phòng khi chạy trên máy chủ tại Việt Nam.
\end{itemize}

\subsubsection{Server-side Data Fetching và song song hóa với \texttt{Promise.all}}
Nhằm loại bỏ hoàn toàn hiện tượng tắc nghẽn thác nước (Waterfall Problem) khi tải nhiều thể loại phim cùng lúc trên Trang chủ, nhóm áp dụng giải pháp đồng thời hóa thông qua \texttt{Promise.all}:

// app/page.tsx
export default async function HomePage() {
  const [
    trending,
    topRated,
    actionMovies,
    comedyMovies,
    horrorMovies,
    animeMovies,
    sciFiMovies
  ] = await Promise.all([
    getTrendingMovies(),
    getTopRatedMovies(),
    getMoviesByGenre(28),   // Action
    getMoviesByGenre(35),   // Comedy
    getMoviesByGenre(27),   // Horror

  ]);

  return (
    <main className="min-h-screen bg-[#141414] pb-24">
      <HeroBanner movie={trending[0]} />
      <div className="-mt-16 sm:-mt-24 md:-mt-32 relative z-20 space-y-6">
        <MovieRow title="Phim Thinh Hanh" movies={trending} />
        <MovieRow title="Danh Gia Cao Nhat" movies={topRated} />
        <MovieRow title="Hanh Dong Kich Tinh" movies={actionMovies} />
        <MovieRow title="Phim Hai Dac Sac" movies={comedyMovies} />

  );
}
\end{lstlisting}

\subsubsection{Dynamic Routing (\texttt{/movie/[id]}) và Dynamic SEO Metadata}
Trang chi tiết phim áp dụng quy ước định tuyến động \texttt{app/movie/[id]/page.tsx}. Kể từ Next.js 15, tham số \texttt{params} đã chuyển sang dạng Promise bất đồng bộ và trở thành quy chuẩn bắt buộc trong Next.js 16, yêu cầu xử lý chuẩn xác bằng cú pháp \texttt{await}:
\begin{lstlisting}[language=TypeScript]
// app/movie/[id]/page.tsx
interface PageProps {
  params: Promise<{ id: string }>;
}

export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { id } = await params;
  const movie = await getMovieDetails(id);
  if (!movie) return { title: 'Khong tim thay phim | MovieHub' };

  return {
    title: `${movie.title} (${movie.release_date.slice(0, 4)}) | MovieHub`,
    description: movie.overview,
    openGraph: {
      title: movie.title,
      description: movie.overview,
      images: [`https://image.tmdb.org/t/p/w1280${movie.backdrop_path}`],
    },
  };
}
\end{lstlisting}

\subsubsection{Cơ chế DNS Fallback Resolver can thiệp \texttt{dns.lookup}}
Trong mã nguồn thực tế \texttt{services/tmdb.ts}, nhóm can thiệp trực tiếp vào hàm phân giải \texttt{dns.lookup} của Node.js kết hợp đối tượng \texttt{Resolver} để chuyển tiếp truy vấn tên miền \texttt{themoviedb.org} qua máy chủ Google DNS và Cloudflare (xem Phụ lục 3):
\begin{lstlisting}[language=TypeScript]
// services/tmdb.ts - Can thiep dns.lookup tren Node.js Server Runtime
import dns from "node:dns";

if (typeof window === "undefined" && dns && dns.lookup) {
  const origLookup = dns.lookup;
  const resolver = new dns.promises.Resolver();
  resolver.setServers(["8.8.8.8", "1.1.1.1"]);

  // @ts-expect-error Node.js internal lookup overload
  dns.lookup = function (hostname: string, options: unknown, callback: unknown) {
    let cb = callback as Function;
    let opt = (typeof options === "function" ? {} : options) as any;
    if (typeof options === "function") cb = options;

    if (hostname && hostname.includes("themoviedb.org")) {
      resolver.resolve4(hostname)
        .then((addrs) => {
          if (opt && opt.all) cb(null, addrs.map((a) => ({ address: a, family: 4 })));
          else cb(null, addrs[0], 4);
        })
        .catch(() => Reflect.apply(origLookup, dns, [hostname, opt, cb]));
    } else {
      Reflect.apply(origLookup, dns, [hostname, opt, cb]);
    }
  };
}
\end{lstlisting}

Giải pháp này khắc phục triệt để hạn chế của hàm \texttt{dns.setServers()} (vốn chỉ ảnh hưởng \texttt{dns.resolve*} mà không tác động tới \texttt{dns.lookup} của \texttt{fetch}), bảo đảm các truy vấn API luôn thông suốt trên hạ tầng mạng Việt Nam mà chỉ thực thi trên Node.js server runtime mà không ảnh hưởng phía client.

\subsubsection{Thuật toán khử trùng lặp phim (\texttt{deduplicateMovies})}
Khi kết hợp dữ liệu từ nhiều trang TMDB để gom đủ 24 phim/trang, nguy cơ xuất hiện các bộ phim trùng nhau là rất cao. Nhóm xây dựng hàm khử trùng lặp dựa trên cấu trúc dữ liệu \texttt{Set} (xem Phụ lục 4):
\begin{lstlisting}[language=TypeScript]
function deduplicateMovies(movies: Movie[]): Movie[] {
  const seen = new Set<number>();
  const unique: Movie[] = [];
  for (const movie of movies) {
    if (movie && movie.id && !seen.has(movie.id)) {
      seen.add(movie.id);
      unique.push(movie);
    }
  }
  return unique;
}
\end{lstlisting}

\subsubsection{Thực nghiệm đối chứng thời gian phản hồi (TTFB) của Streaming Suspense}
Để đánh giá định lượng lợi ích của kỹ thuật Streaming UI với React Suspense, nhóm thiết lập một thử nghiệm đối chứng khoa học trên tuyến đường chi tiết phim \texttt{/movie/[id]}:
\begin{itemize}[noitemsep]
    \item \textbf{Môi trường đo lường:} Bản build Production (\texttt{npm run build \&\& npm run start}), Node.js v22 runtime trên cổng 3000, kết nối trực tiếp ra TMDB API qua đường truyền Internet thực tế (không sử dụng hàm \texttt{setTimeout} giả lập). Dữ liệu được đo lường trung bình qua 10 lượt truy vấn liên tiếp ($\mu \pm \sigma$).
    \item \textbf{Kịch bản A (SSR truyền thống -- Chặn toàn bộ):} Máy chủ bắt buộc phải đợi đồng thời cả 3 truy vấn: Thông tin phim (~150ms), Dàn diễn viên (~450ms) và Phim tương tự (~150ms xử lý/overhead mạng) hoàn thành toàn bộ thì mới bắt đầu gửi byte HTML đầu tiên về client.
    \item \textbf{Kịch bản B (Áp dụng React Suspense Streaming):} Máy chủ chỉ cần hoàn tất truy vấn chính Thông tin phim (~150ms) cộng với thời gian kết xuất khung giao diện ban đầu (~30ms) là lập tức gửi chunk HTML đầu tiên về trình duyệt; hai phần còn lại tiếp tục được stream về sau qua cùng kết nối HTTP đang mở.
\end{itemize}

Bảng 4.5 ghi nhận số liệu đo lường trung bình và độ lệch chuẩn qua 10 lượt thử nghiệm thực tế.

\paragraph*{1. Tóm tắt kết quả đạt được}
Trải qua 7 tuần nghiên cứu chuyên sâu và triển khai thực nghiệm nghiêm túc, nhóm sinh viên đã hoàn thành xuất sắc đồ án môn học Các Công nghệ Lập trình Hiện đại với những kết quả cụ thể:
\begin{enumerate}[noitemsep]
    \item \textbf{Làm chủ công nghệ Next.js 16 và React 19:} Nắm vững và ứng dụng triệt để kiến trúc App Router, phân định ranh giới tường minh giữa Server Components và Client Components, làm chủ cơ chế truyền luồng dữ liệu Streaming với React Suspense và cơ chế Server Actions.
    \item \textbf{Xây dựng ứng dụng hoàn chỉnh và đạt độ thẩm mỹ cao:} Phát triển thành công hệ sinh thái điện ảnh \textbf{MovieHub} với đầy đủ các tính năng: Trang chủ đa chủ đề, Tìm kiếm nhanh Live Search, Bộ lọc đa chiều 5 tiêu chí \texttt{/browse}, Chi tiết phim đa tầng \texttt{/movie/[id]}, Danh sách yêu thích Watchlist lưu qua Cookie bảo mật, và Phim truyền hình \texttt{/tv}.
    \item \textbf{Đạt các chỉ tiêu hiệu năng vượt trội:} Điểm số Google Lighthouse đạt mức gần như tuyệt đối (98--100 điểm); chỉ số ổn định bố cục CLS đạt mức hoàn hảo 0.000; thời gian phản hồi byte đầu tiên (TTFB) giảm 76\% nhờ kỹ thuật Streaming; kích thước bundle JavaScript nạp ban đầu giảm từ 75.1\% đến 84.1\% so với kiến trúc SPA truyền thống.
    \item \textbf{Xử lý bài toán kỹ thuật thực tế:} Hiện thực thành công cơ chế DNS Fallback Resolver, giúp ứng dụng duy trì kết nối ổn định và đáng tin cậy trên hạ tầng mạng Internet tại Việt Nam.
\end{enumerate}

\paragraph*{2. Những hạn chế còn tồn tại}
Mặc dù đã đạt được nhiều kết quả ấn tượng về mặt công nghệ, hệ thống vẫn còn một số điểm có thể hoàn thiện thêm:
\begin{itemize}[noitemsep]
    \item \textbf{Cơ chế xác thực người dùng tập trung:} Hệ thống hiện đang lưu trữ danh sách Watchlist trên Cookie của từng trình duyệt cá nhân; chưa tích hợp hệ thống cơ sở dữ liệu phân tán (như PostgreSQL, MongoDB) kết hợp hệ thống xác thực người dùng (NextAuth/Clerk) để đồng bộ hóa danh sách xem phim trên nhiều thiết bị khác nhau.
    \item \textbf{Hỗ trợ phát phim trực tiếp:} Do giới hạn bản quyền thương mại của TMDB, ứng dụng hiện tại chỉ hỗ trợ xem video giới thiệu (Trailer) chính thức qua YouTube Player API chứ chưa phát trực tiếp toàn bộ nội dung phim.
    \item \textbf{Thách thức kỹ thuật đặc thù từ nền tảng Next.js:} Quá trình phát triển và kiểm thử đã làm sáng tỏ một số hạn chế khách quan của hệ sinh thái Next.js: Vòng đời thay đổi API nhanh (API churn giữa các phiên bản 14, 15 và 16) khiến việc duy trì mã nguồn và kiểm soát deprecation đòi hỏi chi phí bảo trì lớn; kiến trúc bộ nhớ đệm đa tầng (Multi-tier Cache) tuy mạnh mẽ nhưng có độ phức tạp cao, đòi hỏi phân định ranh giới khắt khe giữa ISR theo thời gian và On-demand revalidation; đồng thời việc duy trì máy chủ Node.js trong môi trường sản xuất phát sinh gánh nặng quản trị hạ tầng và chi phí tài nguyên máy chủ so với giải pháp tĩnh hóa hoàn toàn (Static Export qua Edge CDN).
\end{itemize}

\paragraph*{3. Hướng phát triển trong tương lai}
Trong các giai đoạn tiếp theo, nhóm đề xuất các hướng nâng cấp và mở rộng hệ thống:
\begin{enumerate}[noitemsep]
    \item \textbf{Tích hợp hệ quản trị cơ sở dữ liệu Supabase/PostgreSQL:} Chuyển đổi dữ liệu Watchlist và lịch sử xem phim từ Cookie sang cơ sở dữ liệu đám mây có bảo mật phân quyền Row Level Security (RLS).
    \item \textbf{Cơ chế gợi ý phim cá nhân hóa bằng Trí tuệ nhân tạo (AI Recommendation):} Ứng dụng mô hình nhúng vector (Vector Embeddings) để phân tích sở thích xem phim của người dùng và đề xuất các tác phẩm có nội dung tương đồng một cách thông minh.
    \item \textbf{Tối ưu hóa Progressive Web App (PWA):} Bổ sung Service Worker và Web App Manifest cho phép người dùng cài đặt MovieHub trực tiếp lên màn hình chính của điện thoại thông minh và hỗ trợ lưu trữ dữ liệu xem ngoại tuyến (Offline Caching).
\end{enumerate}

\subsection*{Phụ lục 1. Cơ chế xử lý Server Action tìm kiếm nhanh \texttt{quickSearchAction}}
\begin{lstlisting}[language=TypeScript]
// app/actions/search.ts - Server Action tim kiem Live Preview tren Navbar
"use server";

import { searchQuickLive } from "@/services/tmdb";
import type { Movie } from "@/types/tmdb";

/**
 * Server Action tim kiem nhanh cho Live Preview tren Navbar
 * Bao mat TMDB_API_KEY tren server va tra ve toi da 5 ket qua rut gon.
 * Ap dung kiem thuc du lieu dau vao (Input Validation & Sanitization) phia server.
 */
export async function quickSearchAction(query: string): Promise<Movie[]> {
  if (!query || typeof query !== "string") {
    return [];
  }

  const trimmed = query.trim();
  // Gioi han do dai tu 2 den 100 ky tu
  if (trimmed.length < 2 || trimmed.length > 100) {
    return [];
  }

  // Loai bo cac ky tu dieu khien nguy hiem (control characters)
  const sanitized = trimmed.replace(/[\x00-\x1F\x7F]/g, "");
  if (!sanitized) {
    return [];
  }

  return searchQuickLive(sanitized);
}
\end{lstlisting}

\subsection*{Phụ lục 2. Thuật toán lựa chọn Trailer video YouTube tối ưu \texttt{selectBestTrailer}}
\begin{lstlisting}[language=TypeScript]
// services/tmdb.ts - Thuat toan lua chon trailer YouTube toi uu
import type { MovieVideo } from "@/types/tmdb";

export function selectBestTrailer(videos: MovieVideo[]): MovieVideo | null {
  if (!videos || videos.length === 0) return null;

  const youtubeVideos = videos.filter((v) => v.site === "YouTube" && v.key);
  if (youtubeVideos.length === 0) return null;

  // 1. Trailer tieng Viet chinh thuc
  const viOfficialTrailer = youtubeVideos.find(
    (v) => v.type === "Trailer" && v.official && v.iso_639_1 === "vi"
  );
  if (viOfficialTrailer) return viOfficialTrailer;

  // 2. Trailer tieng Viet bat ky
  const viTrailer = youtubeVideos.find(
    (v) => v.type === "Trailer" && v.iso_639_1 === "vi"
  );
  if (viTrailer) return viTrailer;

  // 3. Trailer chinh thuc bat ky (official === true)
  const officialTrailer = youtubeVideos.find(
    (v) => v.type === "Trailer" && v.official
  );
  if (officialTrailer) return officialTrailer;

  // 4. Trailer YouTube bat ky
  const anyTrailer = youtubeVideos.find((v) => v.type === "Trailer");
  if (anyTrailer) return anyTrailer;

  // 5. Teaser YouTube bat ky
  const anyTeaser = youtubeVideos.find((v) => v.type === "Teaser");
  if (anyTeaser) return anyTeaser;

  // 6. Video YouTube dau tien trong danh sach
  return youtubeVideos[0] || null;
}
\end{lstlisting}

\subsection*{Phụ lục 3. Cơ chế tự phân giải tên miền dự phòng DNS Fallback Resolver và hàm \texttt{fetchTMDB}}
\begin{lstlisting}[language=TypeScript]
// services/tmdb.ts - Monkey-patching dns.lookup va ham fetchTMDB voi ISR Cache
import dns from "node:dns";

// Tu dong phan giai DNS cho api.themoviedb.org qua Google DNS & Cloudflare
// de giai quyet triet de loi ENOTFOUND / ISP block tai Viet Nam
if (typeof window === "undefined" && dns && dns.lookup) {
  const origLookup = dns.lookup;
  const resolver = new dns.promises.Resolver();
  resolver.setServers(["8.8.8.8", "1.1.1.1"]);

  // @ts-expect-error Node.js internal lookup overload
  dns.lookup = function (hostname: string, options: unknown, callback: unknown) {
    let cb = callback as (err: Error | null, address?: unknown, family?: number) => void;
    let opt = options as Record<string, unknown> | undefined;
    if (typeof options === "function") {
      cb = options as typeof cb;
      opt = {};
    }

    if (hostname && hostname.includes("themoviedb.org")) {
      resolver
        .resolve4(hostname)
        .then((addresses) => {
          if (opt && opt.all) {
            cb(null, addresses.map((a) => ({ address: a, family: 4 })));
          } else {
            cb(null, addresses[0], 4);
          }
        })
        .catch(() => {
          Reflect.apply(origLookup, dns, [hostname, opt, cb]);
        });
    } else {
      Reflect.apply(origLookup, dns, [hostname, opt, cb]);
    }
  };
}

async function fetchTMDB<T>(
  endpoint: string,
  revalidateTime: number = 3600,
  language: string = "vi-VN"
): Promise<T> {
  if (!TMDB_API_KEY || TMDB_API_KEY === "your_actual_api_key_here") {
    throw new Error("TMDB_API_KEY chua duoc thiet lap.");
  }

  const delimiter = endpoint.includes("?") ? "&" : "?";
  const langParam = language ? `&language=${language}` : "";
  const url = `${TMDB_BASE_URL}${endpoint}${delimiter}api_key=${TMDB_API_KEY}${langParam}`;

  const res = await fetch(url, {
    next: { revalidate: revalidateTime },
  });

  if (!res.ok) {
    throw new Error(`Loi goi API TMDB [${res.status}]: ${res.statusText}`);
  }

  return res.json() as Promise<T>;
}
\end{lstlisting}

\subsection*{Phụ lục 4. Thuật toán khử trùng lặp dữ liệu phim theo ID \texttt{deduplicateMovies}}
\begin{lstlisting}[language=TypeScript]
// services/tmdb.ts - Thuat toan khu trung lap du lieu phim theo ID
import type { Movie } from "@/types/tmdb";

function deduplicateMovies(movies: Movie[]): Movie[] {
  const seen = new Set<number>();
  const unique: Movie[] = [];
  for (const movie of movies) {
    if (movie && movie.id && !seen.has(movie.id)) {
      seen.add(movie.id);
      unique.push(movie);
    }
  }
  return unique;
}
